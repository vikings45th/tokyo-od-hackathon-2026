| | |

#### CKAN API

CKAN の標準APIでデータセット・リソース・組織のメタデータを取得できます。
**以下はすべて 2026-08-20 に実際に叩いて200が返ることを確認済みです**
（認証不要・APIキー不要）：

```
# データセットの検索
https://catalog.data.metro.tokyo.lg.jp/api/3/action/package_search?q=<キーワード>&rows=20

# データセットの詳細（リソースのURLが取れる）
https://catalog.data.metro.tokyo.lg.jp/api/3/action/package_show?id=<データセットID>

# 組織の一覧
https://catalog.data.metro.tokyo.lg.jp/api/3/action/organization_list

# グループ（カテゴリ）の一覧
https://catalog.data.metro.tokyo.lg.jp/api/3/action/group_list
```

`package_search` でキーワードから当たりを付け、`package_show` で
実データ（CSV/JSON等）のURLを取る、という流れになります。

> 💡 **まずやること**：`package_search` を叩いて、候補テーマに関連する
> データセットが実在するかを確認する。アイデアが先行してデータが無い、
> というのが一番痛いパターンです。

#### 形式別のリソース件数（2026-08-20 実測）

`package_search?q=res_format:<形式>&rows=0` の `count` です。

| 形式 | データセット数 | メモ |
|---|---|---|
| CSV | 6,199 | **主戦力。ここから選ぶ** |
| XLSX | 1,156 | パースが面倒。CSV版があるか先に確認 |
| PDF | 538 | 実質使えない。避ける |
| GeoJSON | 35 | **地図系をやるなら要注意：これだけ少ない** |
| SHP | 4 | |
| JSON | 3 | |

**地図で見せる企画をやるなら、GeoJSON が35件しかない前提で組んでください。**
住所や緯度経度を含むCSVからこちらでジオメトリを作る、という工程が
だいたい必要になります。

#### 実データ取得の実例

`package_show` で返る `resources[].url` は `www.opendata.metro.tokyo.lg.jp`
配下を指すことが多く、そこから直接CSVがDLできます（実測済み）。

```bash
curl -sSL -o out.csv "https://www.opendata.metro.tokyo.lg.jp/<パス>.csv"
```

**文字コードは CP932（Shift_JIS）のものが混ざります。** UTF-8決め打ちで
読むと化けるので、`iconv -f cp932 -t utf-8` を通すか、
パース側でエンコーディングを判定してください。
また1行目がタイトル行で、実際のヘッダが3行目、という構造のファイルもあります。
`data/` に置く前に正規化する工程を見込んでおいてください。

#### カタログサイトで使える機能

公式トップページによると、カタログサイトには以下があります。

- **オープンデータの活用事例を一覧で検索できる**
  — 既存サービスとの差別化を考えるときに見ておく価値があります
- **オープンデータへのアクセスランキング**
  — **どのデータがよく使われているかが分かります。**
  人気データは使いやすい（＝形式が整っている）可能性が高い一方、
  他チームと被りやすいとも読めます。両面から見てください
- **必要なオープンデータのリクエスト送信**

もう一つ、**東京都オープンデータコミュニティ**があります。
利用者同士や都との繋がりを作る取り組みで、データについて相談できる場です。

## データ選定のチェックリスト

候補を見つけたら、実装に入る前にこれを確認してください。
**当日に「使えなかった」と分かるのが最悪です。**

- [ ] **実際にダウンロード／API取得できるか**（リンク切れは普通にある）
- [ ] **形式**：CSV / JSON / GeoJSON / Excel / PDF
      — **PDFしか無いデータはこの日程では厳しい**
- [ ] **文字コード**：Shift_JIS のCSVが混ざっていることがある。UTF-8 変換が必要か
- [ ] **更新頻度**：年1回更新か、リアルタイムか
- [ ] **粒度**：都全体か、区市町村単位か、施設単位か
- [ ] **座標**：地図で使うなら緯度経度が入っているか。住所しか無いならジオコーディングが要る
- [ ] **ライセンス**：CC BY 4.0 か、それ以外か
- [ ] **CORS**：ブラウザから直接叩けるか。ダメなら Workers 経由でプロキシする
      （`docs/05-tech.md`）

## ライセンスと出典表記

東京都オープンデータカタログのデータは多くが **CC BY 4.0** ですが、
**データセットごとに異なります。必ず個別に確認してください。**

### 作品に必ず入れること

- 使用したデータセット名
- 提供元（東京都○○局 など）
- ライセンス表記
- 取得日（データが更新される場合）

**出典明記は大会の趣旨そのものであり、審査観点にも直結します。**
「オープンデータが有効に活用されているか」を見られる以上、
何をどう使ったかが分からない作品は評価されません。

### 記載例

```
出典：東京都オープンデータカタログサイト「〇〇データ」（東京都〇〇局）
      https://catalog.data.metro.tokyo.lg.jp/dataset/xxxxx
      CC BY 4.0 / 2026-08-XX 取得
```

## 使用データセット一覧【提出物です】→ `data/SOURCES.md`

> ⚠️ **一覧の置き場所は `data/SOURCES.md` の1箇所です。ここには表を置きません。**
> 2箇所に分けると必ず片方が漏れます。**オーナーは①（データ担当）**
> （[`docs/10-roles-schedule.md`](10-roles-schedule.md)）。

作品提出フォームのエントリー項目⑤が
**「オープンデータの利用状況 — 利用している／利用予定の代表的なオープンデータ（最大10件）」**
です。8/23の当日にまとめようとすると必ず漏れます。**調べた時点で書いてください。**

そして「データ活用」は**審査基準の1項目であり、データ活用賞という賞そのもの**です
（`docs/01-event.md`）。ここの丁寧さが直接得点になります。

`data/SOURCES.md` に書く項目（そのまま提出フォームに転記できる形で）：

| データセット名 | 提供元 | 形式 | 粒度 | ライセンス | URL | 取得日 |
|---|---|---|---|---|---|---|

**このファイルで調査結果を共有したい場合は、上の「実測したデータの中身と落とし穴」節に
追記してください。**（落とし穴の記録＝ここ、提出用の一覧＝`data/SOURCES.md`）
