## 0. 設計の前に — 数値検証で判明した2つの事実

**設計を確定させる前に、指標が本当に機能するかを実データで計算しました。**
2つとも設計を左右するので、最初に書きます。

### 0-1. ⛔ 江戸川区を除外しないと、常に「都内最悪の区」になる

`trend = +1.5pt/年` でリスクスコアを試算した結果（令和12年度）：

```
江戸川区 95  ← ⛔ 偽陽性。制度が別枠（全児童対象「すくすくスクール」）で登録率0.004のため
中央区   67     品川区 41   稲城市 31   昭島市 31   中野区 30  …  渋谷区 1
```

**江戸川区の登録率が極端に低いのは受け皿が無いからではなく、制度が違うからです。**
そのままスコア計算に入れると需要が爆発し、**必ず最上位に固定されます。**
購入エリアの推薦でこれをやると誤情報になります。

→ **設計要件**：江戸川区は**スコア対象から除外し、別枠で注記付き表示**する（§4-4）。

### 0-2. 🔴 登録率トレンドがモデルを支配している

同じ計算を `trend` を変えて回した結果（令和12年度のスコア分布）：

| trend | 最大 | 中央値 | 最小 | スコア1超えの自治体 |
|---|---|---|---|---|
| **0.0pt/年** | 38 | **0** | 0 | **4 / 49** ⛔ 指標が死ぬ |
| +0.5pt/年 | 86 | 1 | 0 | 26 / 49 |
| **+1.0pt/年** | 92 | 13 | 0 | 45 / 49 |
| **+1.5pt/年** | 95 | 22 | 1 | 48 / 49 |
| +2.0pt/年 | 96 | 28 | 7 | 49 / 49 |

**`trend = 0` だと49自治体中45が0点になります。**
少子化で児童数が減るため、受け皿が今のままでも足りてしまうからです。

**現実に学童が不足しているのは、児童数の減少を上回る速さで登録率が上がっているからです。**
つまり登録率トレンドは「あれば嬉しい補助変数」ではなく、**モデルの中核パラメータ**です。

**そして都のオープンデータにこの値は存在しません**（学童データは令和5年の1時点のみ）。

→ **設計要件**：これを**隠れた仮定にせず、ユーザーが動かす主役のつまみにする**（§4-5）。
本サービスは「単一の予測値を断言するもの」ではなく
「**登録率が上がり続けたら、あなたの区はいつ破綻するか**」を示す**感度分析ツール**です。

**この設計は、単一値を断言するより誠実で、審査でも強い形です。**
そして **生成AI②（自然文→パラメータ変換）の存在意義がここで決定的になります。**

## 3. 指標プラグインの定義【最重要】

**軸を後から足しても、画面もスコア計算も書き直さずに済む構造にします。**
v1は `gakudo` 1つだけ登録し、重み1.0。軸2・軸3はこの配列に足すだけです。

```ts
export interface Indicator {
  id: string;                    // 'gakudo'
  label: string;                 // '学童の受け入れリスク'
  weight: number;                // 総合スコアの重み（v1は 1.0）
  higherIsWorse: true;           // スコアの向き
  /** 1自治体・1入学年度ぶんを計算する。純関数。 */
  compute(input: IndicatorInput): IndicatorResult | null;  // null = 対象外
}

export interface IndicatorInput {
  muni: Muni;                    // data/app/munis.json の1件
  year: number;                  // 入学年度（西暦）
  projection: Projection;        // §5 の予測エンジンの出力
  scenario: Scenario;            // §4-5
}

export interface IndicatorResult {
  score: number;                 // 0〜100（100が最も悪い）
  detail: Record<string, number>;// 画面の詳細表示用（需要・供給・ギャップ 等）
  note?: Note;                   // 注記（§4-4）
  excluded?: boolean;            // true ならスコア対象外・別枠表示
}
```

**総合スコア** `= Σ(indicator.score × indicator.weight) / Σ(weight)`
v1は軸1のみなので `gakudo` のスコアがそのまま総合スコアになります。

> ⚠️ **`compute` は純関数にしてください。** シナリオを変えるたびに
> 49自治体 × 年度ぶん呼ばれます。副作用があると再計算が壊れます。

### 軸を追加する手順（将来）

1. `src/core/indicators/<id>.ts` に `Indicator` を実装する
2. `src/core/indicators/index.ts` の配列に足す
3. **重みを決める**（UIのスライダーに自動で出る）
4. **画面もヒートマップも変更不要**

## 4. 軸1（学童）の指標定義

### 4-1. 記号

| 記号 | 意味 | 出典 |
|---|---|---|
| `N(m,y)` | 自治体 m の年度 y の公立小学校児童数（全学年） | 教育人口等推計＋予測エンジン（§5） |
| `Reg(m)` | 学童登録児童数 | 学童クラブ実施状況（**令和5年5月1日＝2023年度**） |
| `Wait(m)` | 学童待機児童数 | 同上 |
| `N0(m)` | 2023年度の公立小学校児童数（全学年） | 公立学校一覧 令和5年度 |

### 4-2. 計算式

```
顕在需要率     r_latent(m) = (Reg(m) + Wait(m)) / N0(m)
目標需要率     r_target(m,y) = min( r_latent(m) + trend × (y − 2023), 0.60 )
需要           D(m,y) = N(m,y) × r_target(m,y)
供給           S(m,y) = Reg(m) × supplyGrowth(y)          （既定 1.0 ＝ 据え置き）
充足率         Fill   = min( S / D , 1 )
不足人数       Gap    = max( D − S , 0 )
リスクスコア   score  = 100 × (1 − Fill)
```

**`score` は「需要のうち何%が受け皿に入れないか」**という意味です。直感的に読めます。

> **なぜ分子に `Wait` を足すのか**：`Reg` だけでは「実際に入れた人」しか数えられません。
> **申し込んで落ちた人（待機）は需要です。** ただし
> **「申込前に断念した人」はどちらにも入っていません**（`docs/13-requirements.md` §1-2 検証1）。
> **`r_latent` は需要の下限**であり、`trend` がその不足分を吸収する設計です。

> ⚠️ **分母は常に全学年**にします。`Reg` が全学年合計なので、低学年に絞ると分母だけ小さくなり
> 率が過大になります。低学年（1〜3年）の推移は**詳細画面の補助表示**に留めてください。

### 4-3. 基準年のずれ

学童データは**令和5年5月1日（2023年度）**、児童数推計は**令和7年度（2025年度）起点**です。
`r_latent` の分母には**令和5年度の実績児童数 `N0`** を使い、基準年を揃えます。
**このずれは画面の注記に明記します**（`docs/13-requirements.md` NFR-5）。

### 4-4. 外れ値の規則【3種を区別すること】

**同じ「異常値」として潰すと、本物の供給不足が消えます。**

| 種別 | `note.kind` | 判定 | 扱い |
|---|---|---|---|
| **制度が別枠** | `system-difference` | `r_latent < 0.02` かつ `Wait == 0` かつ `Reg/クラブ数` が極端に小さい | ⛔ **`excluded: true`。スコア対象から外し、別枠に注記付きで表示**。**実測：江戸川区（登録141人・クラブ4か所・登録率0.004）** |
| **本物の供給不足** | `real-shortage` | `r_latent` が下位20%かつ `Wait > 0` | ✅ **スコアに含める。上位リスクとして正しく出す**。**実測：中央区（登録774人・15クラブ・待機257人・登録率0.088）** |
| **母数不足** | `small-sample` | `N0 < 500` | ⛔ **対象範囲から除外**（島嶼部・郡部）。**実測：利島村1.455／三宅村1.431** |

> 🔴 **`excluded: true` の自治体をヒートマップの色計算に入れないこと。**
> §0-1 のとおり、入れると江戸川区が常に最上位（95点）に固定されます。

**注記の文面は生成AI③が前処理で生成し、`data/app/notes.json` にコミットします**（§7）。

### 4-5. シナリオ変数

```ts
type Scenario = {
  trend?: number;          // 登録率の年あたり上昇（既定 0.015 ＝ +1.5pt/年）
  supplyGrowth?: number[]; // 年度ごとの供給倍率（既定 すべて 1.0）
  housing?: HousingPlan[]; // 住宅開発（下記）
};
type HousingPlan = {
  muni: string; year: number; units: number;
  type: '都営住宅'|'都民住宅'|'UR賃貸'|'公社2DK'|'公社3DK以上'|'民間マンションA'|'民間マンションB';
};
```

#### `trend` の既定値は **+1.5pt/年。これは暫定値です**

**都のオープンデータに実測値は存在しません**（学童データが1時点のみのため）。
§0-2 のとおり**この値がモデルを支配する**ので、次を必ず守ってください。

- **画面に「仮定」と明示し、スライダーで動かせるようにする**（`docs/13-requirements.md` NFR-5）
- **`docs/13-requirements.md` §10 未解決事項1** でこども家庭庁の複数年度が取れたら、
  **実測値に差し替える**。都の学童CSVの3行目に
  `（こども家庭庁成育局成育環境課実施調査に基づく）` とあり、**都のデータは国の調査の転載**です

#### `housing` は都の公式係数で人数に変換する

`25es_survey`（住宅種別 × 学年別の児童発生率・**1戸あたり**）を使います。**実測値**：

| 住宅種別 | 小1 | 小2 | 小3 | 小4 | 小5 | 小6 | 6学年計 |
|---|---|---|---|---|---|---|---|
| 都営住宅 | 0.059 | 0.054 | 0.050 | 0.047 | 0.044 | 0.042 | 0.296 |
| 都民住宅 | 0.030 | 0.027 | 0.026 | 0.025 | 0.024 | 0.024 | 0.156 |
| UR賃貸 | 0.010 | 0.010 | 0.000 | 0.020 | 0.020 | 0.000 | 0.060 |
| 公社2DK | 0.019 | 0.016 | 0.014 | 0.012 | 0.010 | 0.009 | 0.080 |
| 公社3DK以上 | 0.038 | 0.032 | 0.027 | 0.023 | 0.020 | 0.018 | 0.158 |
| **民間マンションA地区** | **0.013** | 0.011 | 0.010 | 0.009 | 0.008 | 0.007 | **0.058** |
| 民間マンションB地区 | 0.027 | 0.025 | 0.022 | 0.020 | 0.017 | 0.015 | 0.126 |

> 例：**民間マンションA地区 600戸 → 小1が 600 × 0.013 = 7.8人**、6学年合計で 34.8人。
>
> 🔴 **数値を作るのは都の係数であって、LLMではありません。**
> LLMは「言葉 → どの係数をどこに幾つ適用するか」の写像だけを担当します（§7）。

## 5. 共通予測エンジン

### 5-1. 手順

1. **学校別コーホート進級率**
   `r(school,g) = 児童数(R7,g+1) / 児童数(R6,g)`、R6/R5でも同様 → **2年分の平均**
   - `[0.7, 1.3]` でクリップ（統廃合・学区変更による飛び値を潰す）
   - 欠測校（新設・廃校で3年分揃わない）は**自治体平均**で補完
2. **新1年生**：自治体の `就学予定者` 推計を、**その学校の過去3年の1年生シェア**で按分
3. **前進**：`t+1年の学年g = t年の学年(g−1) × r`、1年生は 2. から
4. **raking（整合）**：学校合計が**都の公式推計（自治体×学年）に一致するようスケーリング**

> **4. が設計上の要です。** 都の推計を否定せず**細分化するだけ**という立て付けにできます。
> 行政審査員3人がいる審査構成で効きます。

### 5-2. 予測射程は2段構え

```
全都 小学校1年生数の推計（教育庁 25es_result01・実測）
R7 93,532（実数）→ R12 76,342 → R13 76,616 → R15 75,694 → R20 78,373
                    └ 区市町村別はここで切れる ┘  └─ 全都はここまである ─┘
```

| 入学年度 | 子の現在年齢 | 根拠 | `basis` |
|---|---|---|---|
| **令和9〜13年度（2027〜2031）** | 1〜6歳 | **区市町村別の都の公式推計そのもの** | `official` |
| **令和14〜20年度（2032〜2038）** | 0歳〜未出生 | **全都の公式推計の伸び率**を区市町村のR12値に接続 | `bridged` |
| 令和21年度以降 | — | 根拠なし | **算出しない** |

```
接続式： N(m,y) = N(m,R12) × ( N_全都(y) / N_全都(R12) )     … y ≥ R13
```

**「自前で外挿した」ではなく「都の公式推計どうしを接続した」と言えます。**

> ⚠️ **`bridged` 区間では区ごとの伸びの差が失われます**（全都一律の伸びを仮定するため）。
> **画面に境界線を引き、予測区間を広げてください**（`docs/13-requirements.md` NFR-5）。

### 5-3. 予測区間

**バックテストの実測誤差分布から出します。** 令和5年度版の推計 vs 令和7年度実数（57地区）：

```
平均誤差 +0.26% / 中央値 +0.50% / 絶対誤差平均 1.51%
最大の外し：島部 -6.02% / 国立市 -5.57% / 東大和市 +4.13% / 日の出町 +5.18%
```

| 先の年数 | 帯の出し方 |
|---|---|
| 1年先・2年先 | **実測した誤差分布の p10/p90** |
| 3年先以上（`official`） | 2年先の帯を √(年数/2) で拡大。**外挿だと明記** |
| `bridged` 区間 | 上記に加えて**さらに広げる**。**「測っていない」と明記** |

> 🔴 **実測できるのは1年先と2年先だけです**（推計ヴィンテージが令和5・6・7の3世代しかない）。
> **測っていないことを測ったように書かないでください。** 家の購入判断に使わせる以上の最低条件です。

## 6. スコア・ヒートマップ

### 6-1. ヒートマップ

- **行＝49自治体**（23区 ＋ 多摩26市）／**列＝入学年度**（2027〜2038）
- **セル色＝総合スコア**（0〜100、高いほど悪い）
- **`excluded: true` の自治体は色計算に含めず、表の下に別枠**（§4-4）
- **`basis: 'bridged'` の列は視覚的に区切る**（境界線・淡い網かけなど）
- 行の既定ソートは「ユーザーの子が小1になる年度」のスコア降順

> ⚠️ **カラースケールを書く前に `dataviz` スキルを読んでください**（`docs/05-tech.md`）。
> 連続量なので sequential パレットを使い、**赤緑だけで表現しない**こと。

### 6-2. 軸が増えたときの拡張

- 指標セレクタ（軸ごとの表示切替）
- 重みスライダー → **総合スコア** `= Σ(score × weight) / Σ(weight)`
- **ヒートマップのコンポーネントは変更不要**（セルの値の出どころが変わるだけ）

## 7. 生成AIの3か所

| **③** | **制度差・外れ値の注記生成** | 前処理で1回。**コミット** | 自治体の実測値＋`note.kind` | 注記の文面 | ① |

### なぜAIでないと駄目か（提出項目③にそのまま書けます）

- **①**：学童CSVはヘッダ6行目・区部と市町村部が横並び2ブロック・数値は `"1,261 "` 形式、
  学校一覧は多階層ヘッダ・欠測 `-`、推計は縦持ち＋和暦列。**局ごとに様式が違い毎年変わります。**
  **LLMは値に触らずプランだけ作る**ので、ハルシネーションが数値に混入しません。
  そして `docs/13-requirements.md` §1-2 検証4 で「**そのままでは読めない**」と主張している
  当の問題を、AIで解いていることになります
- **②**：**数値は都の公式係数が出します**（§4-5）。LLMは写像だけ。
  **§0-2 のとおりトレンドがモデルを支配するので、それを自然文で動かせることが中核機能です**
- **③**：数値ルールでは全部「異常値」としか言えません。
  **江戸川区と中央区の違いは制度を読まないと分かりません**（§4-4）

### ②の安全策【必須】

1. **JSONスキーマで検証してから適用する**
2. 検証に落ちたら「解釈できませんでした」を返し、**ベースラインのスコアとヒートマップは
   表示され続ける**（`docs/13-requirements.md` NFR-2）
3. `trend` は `[-0.05, +0.05]`、`units` は `[0, 5000]` にクランプする
4. **APIキーは Secrets Store か環境変数。ソースにも環境変数欄にも書かない**（`CLAUDE.md`）

> ⚠️ **Workers AI のクレジットはチーム$100・追加は承認制**（`docs/05-tech.md`）。
> **①③を前処理に寄せ、実行時に呼ぶのは②だけ**にしてあります。
> **この設計理由がそのまま提出項目③「生成AI等の活用方法」になります。**

## 11. 技術選定

| 項目 | 選択 | 理由（提出項目③にそのまま転記できます） |
|---|---|---|
| 前処理 | **Python 3.11・標準ライブラリのみ** | 環境に導入済み。**pandas を入れない**＝3人の環境差でパイプラインが壊れない |
| フロント | **素の TypeScript ＋ Vite** | 3人全員が触れる。新規学習の余裕なし。型が契約に効く |
| スタイル | **素のCSS（カスタムプロパティ）** | Tailwindの設定に時間を使わない |
| チャート | **自前インラインSVG** | ヒートマップ＋折れ線＋予測区間の帯だけ。**書く前に `dataviz` スキルを読む** |
| 地図 | **使わない** | ジオコーディングAPIが CONNECT 403。自治体単位MVPに不要 |
| データ配信 | **静的JSON** | **実測455KB / gzip150KB**。APIもDBも不要と**測定で言える** |
| 予測計算 | **ブラウザ内（`src/core/`）** | サーバー往復が無駄。**「都の推計モデルをブラウザで再実行」が技術的見せ場** |
| バックエンド | **Pages Functions 1本**（`/api/scenario`） | 生成AI②のためだけ。APIキーをブラウザに出さない最小構成 |
| 生成AI | **Workers AI / Qwen3 30B FP8** | 事務局提供・推奨既定。**$100制約**のため実行時呼び出しは1か所 |
| DB / KV / R2 | **使わない** | 状態を持たない。**特典が間に合わなくても無料プランで動く** |
| デプロイ | **Cloudflare Pages**（ローカルから `wrangler`） | `wrangler login` はブラウザOAuthでクラウドセッションでは完結しない |

```jsonc
// package.json（②がオーナー）
"scripts": {
  "dev":    "vite",
  "build":  "vite build",                 // ⚠️ ネットに行かない。data/ を読むだけ
  "deploy": "wrangler pages deploy dist"  // ローカルマシンから実行
}
```

## 12. リスクと退避策

| リスク | 退避 |
|---|---|
| **Cloudflare特典が間に合わない**（発行1週間の可能性） | **無料プランで Pages は使える。** R2・D1 不使用なので**影響ゼロ** |
| **Workers AI が使えない／$100 を使い切る** | **シナリオをプリセット3つに退避**（マンション600戸／登録率+1pt・+2pt／供給拡大）。**完全静的で成立。** そのため `src/core` のシナリオ適用関数は**LLMと切り離したインターフェース**で切ること |
| **LLMが変なJSONを返す** | スキーマ検証＋クランプ（§7）。**スコアとヒートマップは生き続ける** |
| **①のデータが遅れる** | **`data/sample.json` を先に置く**（`docs/15-interfaces.md`） |
| **登録率トレンドの実測値が手に入らない** | **既定+1.5pt/年のまま、スライダーと感度分析で見せる。** §0-2 のとおり**これはむしろ誠実な形**であり、MVPは成立する |
| **軸2・3を足す時間が無い** | **v1は軸1のみで完結する設計**（§3）。プラグイン構造は「拡張性の説明」として提出文に書ける |
