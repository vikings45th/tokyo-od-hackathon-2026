## 0. 設計の前に — 数値検証で判明した2つの事実

**設計を確定させる前に、指標が本当に機能するかを実データで計算しました。**
2つとも設計を左右するので、最初に書きます。

### 0-1. ⛔ 基準年を2023年にすると、江戸川区が偽陽性で最上位に固定される

**最初 2023年5月（カタログ掲載分）を基準に試算したところ、こうなりました。**

```
江戸川区 95  ← ⛔ 偽陽性。2023-05 は 4クラブ / 登録141人 / 顕在需要率0.004
中央区   67     品川区 41   稲城市 31   昭島市 31   中野区 30  …  渋谷区 1
```

**江戸川区の値が異常なのは受け皿が無いからではなく、計上方法が違ったからです。**

#### ✅ 3時点データで解決しました

`data/processed/gakudou_stats_by_municipality.csv` に**2025年5月・10月**が入ったので、
基準年を **2025年（令和7年5月）** に移せます。

| 時点 | 江戸川区 | 顕在需要率 |
|---|---|---|
| 2023-05-01 | **4クラブ / 登録141人** | **0.004** ⛔ 異常 |
| **2025-05-01** | **72クラブ / 登録6,623人** | **0.212** ✅ 他自治体と比較可能な値 |

**2025年基準なら江戸川区は正常値です。スコア計算からの除外は不要になりました。**

さらに副産物があります。**学童の 2025-05-01 と、公立学校一覧の令和7年度（2025年5月1日）は
同じ基準日です。** 当初「基準年がずれる」を限界として挙げていましたが、**解消しました**（§4-3）。

#### 🔴 ただしトレンド計算からは今も除外が必要です

2023→2025 で **登録141人 → 6,623人**。これをトレンドに入れると
**+20pt/年**という、データの断絶に由来する値になります。

→ **設計要件**：`note.kind = 'series-break'` として**トレンド計算からのみ除外**し、
スコア計算には含める。**画面には注記を出す**（§4-4）。

### 0-2. 🔴 登録率トレンドがモデルを支配している — **実測済み**

リスクスコアを `trend` を変えて試算した結果（令和12年度のスコア分布・49自治体）：

| trend | 最大 | 中央値 | 最小 | スコア1超えの自治体 |
|---|---|---|---|---|
| **0.0pt/年** | 38 | **0** | 0 | **4 / 49** ⛔ 指標が死ぬ |
| +0.5pt/年 | 86 | 1 | 0 | 26 / 49 |
| **+1.0pt/年** | 92 | 13 | 0 | 45 / 49 |
| +1.5pt/年 | 95 | 22 | 1 | 48 / 49 |
| +2.0pt/年 | 96 | 28 | 7 | 49 / 49 |

> ⚠️ **この表はN0の基準訂正（下記）前の試算です。** `src/core/`（予測エンジン・スコア計算）が
> できたら、教育人口等推計の総数を分母にして②が再試算してください。傾向（trendが効くこと）
> 自体は変わりませんが、絶対値はズレます。

**`trend = 0` だと49自治体中45が0点になります。**
少子化で児童数が減るため、受け皿が今のままでも足りてしまうからです。

**現実に学童が不足しているのは、児童数の減少を上回る速さで登録率が上がっているからです。**
つまり登録率トレンドは「あれば嬉しい補助変数」ではなく、**モデルの中核パラメータ**です。

#### ✅ その値を実測しました（`data/processed/gakudou_stats_by_municipality.csv` × 教育人口等推計）

学童データが**3時点（2023-05 / 2025-05 / 2025-10）**に拡張されたので、計算できます。
対象は**48自治体**（23区＋多摩26市から、制度が別枠の江戸川区と母数不足の島嶼部・郡部を除外）。
児童数は**教育人口等推計の総数**（義務教育学校の前期課程を含む。公立学校一覧＝小学校のみの
名簿とは4自治体で最大20%差があるため、こちらを正とする。2026-08-22 決定）。

```
顕在需要率 =（登録児童数 + 待機児童数）÷ 公立小学校児童数

  2023-05：135,143 / 563,282 = 0.2399
  2025-05：143,122 / 558,686 = 0.2562
  → 年あたり +0.0081（+0.81pt/年）／自治体平均 +0.88pt/年・中央値 +0.88pt/年
  → 48自治体中 45 が上昇。p10 +0.28pt / p90 +1.87pt
  → 上位 中央区+2.28pt 東村山市+2.05pt 渋谷区+2.04pt
     下位 豊島区-1.82pt 港区-0.71pt 立川市-0.45pt
```

🔴 **「児童数は減るのに需要は増える」が実証されました。**
児童数は2年で **-0.82%**（563,282→558,686）なのに、
登録+待機は **+5.9%**（135,143→143,122）です。

→ **`Scenario.trend` の既定値は +0.81pt/年（0.0081）に確定。**
　 当初の暫定値 +1.5pt/年 は**過大**でした。
　 ⚠️ **2026-08-23 訂正**：`src/core/constants.ts` の `DEFAULT_TREND` は
　 `0.0084`（N0 訂正前の暫定値）のままになっていました。実データの実測は **0.008128** です。
　 定数・プリセットの説明文・画面表示の3か所に同じ数字を持っていたのが原因で、
　 **説明文からは数字を落とし、実測値を1か所（`measureTrend()`）から出す**形に直しました。

供給側も実測できます。クラブ数は **1,933 → 1,997（+1.6%/年）**。
ただし **`supplyGrowth` の既定は 1.0（据え置き）のまま**にします。
「**何もしなければどうなるか**」を基準線にするためです。

#### 🔴 2026-08-23：自治体別のトレンドを推定する仕組みを入れました（docs/19 依頼3）

**訂正の履歴として残します。** 上の「都平均の1点を全自治体に当てる」は**強い仮定**でした。
`src/core/trend.ts` に自治体別の最小二乗を実装し、`measureTrend().byMuni` で返しています。

```
r_latent(m, t) = (登録 + 待機)(m,t) / 公立小学校児童数(m,t)
b(m) = 年に対する単回帰の傾き、se(m) = その標準誤差（自由度 n−2）
ci(m) = b(m) ± t(0.90, df) × se(m)
```

**ただし、いまのデータでは49自治体すべてがフォールバックします。**
学童は3時点（2023-05 / 2025-05 / 2025-10）ありますが、**2025-10 に対応する児童数が無い**ので
落ち、実質2点＝自由度0で標準誤差が出せません（`MIN_TREND_POINTS = 3` 未満）。

| | 値 |
|---|---|
| 自治体別2点傾きの中央値 | **+0.89pt/年** |
| 同 p10 / p90 | **+0.33pt / +1.87pt** |
| 上位 | 中央区 +2.28pt / 東村山市 / 渋谷区 |
| 下位 | 港区 −0.71pt / 豊島区 |
| 自前で傾きを引けた自治体 | **0 / 49** |

→ フォールバック時の傾きは **`measureTrend().trend`（+0.81pt・都計比）**。
　 自治体別傾きの中央値（+0.89pt）ではなく**画面に出ている数字の方**に揃えています。
　 同じ意味の数字を2つ持つと必ずずれるためです（0.08pt の差は承知のうえ）。
　 信頼区間は**自治体間のばらつき（p10 / p90）**を当てています。

🔴 **足りないのは学童 2024-05-01 の1点だけです。** 分母（児童数）は
`AppData.schools[].actual` が [令和5,6,7] を持っているので既にあります。
①がこの1点を入れると、**コード変更なしで**分子3点 × 分母3点になり最小二乗が成立します。
そのときは縮約推定（`τ² = max(0, var(b) − mean(se²))`）が同時に効き、
標準誤差の大きい自治体は都平均に寄ります（3点＝自由度1の極端な傾きが13年外挿されるのを防ぐため）。

#### 🔴 予測区間にトレンドの不確かさを入れました（同日・依頼3-4）

それまでの `demandBand` は `児童数の帯 × r_target` で、**児童数の推計誤差しか入っていません**でした。
モデルを支配しているのは上の表のとおりトレンドの方なので、
**支配的な不確実性が入っていないものを「予測区間」と呼ぶのは、この作品の建前に反します。**

```
relN = (児童数の帯の下限 − 児童数) / 児童数     ← backtest 由来
relR = (r_lo − r_target) / r_target             ← 傾きの信頼区間由来
demandBand.lo = demand × (1 − √(relN² + relR²))    独立と仮定して二乗和平方根
gapBand.lo    = max(demandBand.lo − supply, 0)     供給は推定でなく仮定なので帯を持たない
```

実測（中央区・2031年度）：

| | 下限 | 上限 | 幅 |
|---|---|---|---|
| 旧 `demandBand`（児童数の誤差だけ） | 2,056.1 | 2,282.5 | 226.4 |
| **新 `demandBand`** | **1,855.1** | **2,834.7** | **979.6（4.3倍）** |
| **新 `gapBand`**（gap 882人） | **564.1** | **1,543.7** | — |

> ⚠️ **「独立と仮定した」こと自体が仮定です。** 児童数が伸びる区は登録率も上がる、という
> 相関はあり得ますが、実測できていないので独立としました。単純に `帯の下限 × r_lo` と
> 掛け合わせると、独立な2つの10%点の積は実質2〜3%点に相当し、帯が過大になります。

#### それでも「つまみ」であることは変えません

実測値が入っても、**この1つの値が結果を支配する**構造は変わりません。
p10 +0.28pt 〜 p90 +1.87pt と**自治体間のばらつきが大きい**（豊島区は下降）ので、
都平均の1点を全自治体に当てるのは強い仮定です。

→ **画面ではスライダーで動かせるようにし、既定値の根拠を明示します**（要件 NFR-5）。
本サービスは「単一の予測値を断言するもの」ではなく
「**登録率がこの傾きで上がり続けたら、あなたの区はいつ破綻するか**」を示す**感度分析ツール**です。

**この設計は、単一値を断言するより誠実で、審査でも強い形です。**
そして **生成AI②（自然文→パラメータ変換）の存在意義がここで決定的になります。**

## 3. 指標プラグインの定義【最重要】

**軸を後から足しても、画面もスコア計算も書き直さずに済む構造にします。**
v1は `gakudo` 1つだけ登録し、重み1.0。軸2・軸3はこの配列に足すだけです。

```ts
export interface Indicator {
  id: string;                    // 'gakudo'
  label: string;                 // '学童の受け入れリスク'
  weight: number;                // 総合スコアの重み（v1は 1.0）
  higherIsWorse: true;           // スコアの向き
  /** 1自治体・1入学年度ぶんを計算する。純関数。 */
  compute(input: IndicatorInput): IndicatorResult | null;  // null = 対象外
}

export interface IndicatorInput {
  muni: Muni;                    // data/app/munis.json の1件
  year: number;                  // 入学年度（西暦）
  projection: Projection;        // §5 の予測エンジンの出力
  scenario: Scenario;            // §4-5
}

export interface IndicatorResult {
  score: number;                 // 0〜100（100が最も悪い）
  detail: Record<string, number>;// 画面の詳細表示用（需要・供給・ギャップ 等）
  note?: Note;                   // 注記（§4-4）
  excluded?: boolean;            // true ならスコア対象外・別枠表示
}
```

**総合スコア** `= Σ(indicator.score × indicator.weight) / Σ(weight)`
v1は軸1のみなので `gakudo` のスコアがそのまま総合スコアになります。

> ⚠️ **`compute` は純関数にしてください。** シナリオを変えるたびに
> 49自治体 × 年度ぶん呼ばれます。副作用があると再計算が壊れます。

### 軸を追加する手順（将来）

1. `src/core/indicators/<id>.ts` に `Indicator` を実装する
2. `src/core/indicators/index.ts` の配列に足す
3. **重みを決める**（UIのスライダーに自動で出る）
4. **画面もヒートマップも変更不要**

## 4. 軸1（学童）の指標定義

### 4-1. 記号

| 記号 | 意味 | 出典 |
|---|---|---|
| `N(m,y)` | 自治体 m の年度 y の公立小学校児童数（全学年） | 教育人口等推計＋予測エンジン（§5） |
| `Reg(m)` | 学童登録児童数 | 学童クラブ実施状況 **2025-05-01（令和7年5月）** |
| `Wait(m)` | 学童待機児童数 | 同上 |
| `N0(m)` | **2025年度**の公立小学校児童数（全学年。義務教育学校の前期課程を含む） | 教育人口等推計 **令和7年度（2025年5月1日現在）**。2026-08-22 決定：公立学校一覧（小学校のみの名簿）は義務教育学校を含まず4自治体で最大20%少ないため不採用 |

### 4-2. 計算式

```
顕在需要率     r_latent(m) = (Reg(m) + Wait(m)) / N0(m)
目標需要率     r_target(m,y) = min( r_latent(m) + trend × (y − 2025), 0.60 )
需要           D(m,y) = N(m,y) × r_target(m,y)
供給           S(m,y) = Reg(m) × supplyGrowth(y)          （既定 1.0 ＝ 据え置き。実測はクラブ数 +1.6%/年）
充足率         Fill   = min( S / D , 1 )
不足人数       Gap    = max( D − S , 0 )
リスクスコア   score  = 100 × (1 − Fill)
```

**`score` は「需要のうち何%が受け皿に入れないか」**という意味です。直感的に読めます。

> **なぜ分子に `Wait` を足すのか**：`Reg` だけでは「実際に入れた人」しか数えられません。
> **申し込んで落ちた人（待機）は需要です。** ただし
> **「申込前に断念した人」はどちらにも入っていません**（`docs/13-requirements.md` §1-2 検証1）。
> **`r_latent` は需要の下限**であり、`trend` がその不足分を吸収する設計です。

> ⚠️ **分母は常に全学年**にします。`Reg` が全学年合計なので、低学年に絞ると分母だけ小さくなり
> 率が過大になります。低学年（1〜3年）の推移は**詳細画面の補助表示**に留めてください。

### 4-3. ✅ 基準年のずれは解消しました

当初は学童が令和5年5月1日、推計が令和7年度起点でずれていましたが、
**3時点データで学童の 2025-05-01 が使えるようになり、
教育人口等推計の令和7年度（2025年5月1日現在）と基準日が一致しました。**

```
学童（登録・待機・クラブ数）  2025-05-01
公立小学校児童数（実績）      2025-05-01（令和7年度）
都の児童数推計                令和7年度起点
```

**3つとも揃っています。** 当初の限界が1つ消えました。

### 4-4. 注記と除外の規則【3種を区別すること】

**同じ「異常値」として潰すと、本物の供給不足が消えます。**
**そして「除外」には2種類あります。何から除外するのかを取り違えないでください。**

| 種別 | `note.kind` | 判定 | 扱い |
|---|---|---|---|
| **系列の断絶** | `series-break` | 2023-05 と 2025-05 で `registered` が**3倍以上**変化 | 🔴 **トレンド計算からのみ除外。スコア計算には含める。** 注記を出す。**実測：江戸川区（141人 → 6,623人）** |
| **本物の供給不足** | `real-shortage` | `r_latent` が下位20%かつ `Wait > 0` | ✅ **スコアに含める。上位リスクとして正しく出す。** **実測：中央区（2025-05 登録1,291人・待機275人・顕在需要率0.163。待機÷登録は17.6%で都内最大）** |
| **母数不足** | `small-sample` | `N0 < 500` | ⛔ **対象範囲から除外**（島嶼部・郡部）。**実測：利島村（母数11人）** |

> 🔴 **`series-break` をスコアから除外しないこと。**
> 2025年基準では江戸川区は顕在需要率0.212で、48自治体中では下位寄りですが
> 他自治体と比較可能な値の範囲内です（§0-1）。
> 除外すると、31,226人の児童を抱える区が画面から消えます。
>
> 🔴 **`series-break` をトレンド計算に入れないこと。**
> 江戸川区を入れると都平均のトレンドが +0.81pt/年 から大きく歪みます。

**注記の文面は生成AI③が前処理で生成し、`data/app/data.json` の `munis[].note` に統合してコミットします**（§7）。

## 5. 共通予測エンジン

### 5-1. 手順

> ## 🔴 v1 では未実装です（2026-08-23 決定・docs/19 依頼2）
>
> **この節（学校別コーホート → raking）は実装していません。** 理由：
>
> - **raking の出力は、定義上（恒等的に）自治体×学年の公式値と一致します。**
>   そして指標が使うのは `projection.children`（自治体×全学年合計）だけなので、
>   **スコアもヒートマップも1つも数字が変わりません**（`src/core/forecast.ts` 冒頭に同じ記述）
> - 学校粒度を画面に出す案は `docs/13-requirements.md` §4 で却下済み（受け入れ枠が区単位でしか存在しない）
> - bridged 区間を学校別コーホートで補正する案は、「**都の公式推計どうしを接続した**」という
>   立て付けを自分で捨てることになるうえ、6年先なので検証不能
>
> **実装しているのは `Muni.official`（都の公式推計そのもの）を読むところまで**で、
> bridged 区間は §5-2 の掛け算1回です。**書いてあることと実物を食い違わせない**ために明記します。
> 以下は「やるとしたらこうする」という設計であって、v1 のコードではありません。

1. **学校別コーホート進級率**
   `r(school,g) = 児童数(R7,g+1) / 児童数(R6,g)`、R6/R5でも同様 → **2年分の平均**
   - `[0.7, 1.3]` でクリップ（統廃合・学区変更による飛び値を潰す）
   - 欠測校（新設・廃校で3年分揃わない）は**自治体平均**で補完
2. **新1年生**：自治体の `就学予定者` 推計を、**その学校の過去3年の1年生シェア**で按分
3. **前進**：`t+1年の学年g = t年の学年(g−1) × r`、1年生は 2. から
4. **raking（整合）**：学校合計が**都の公式推計（自治体×学年）に一致するようスケーリング**

> **4. が設計上の要です。** 都の推計を否定せず**細分化するだけ**という立て付けにできます。
> 行政審査員3人がいる審査構成で効きます。

- **①**：学童CSVはヘッダ6行目・区部と市町村部が横並び2ブロック・数値は `"1,261 "` 形式、
  学校一覧は多階層ヘッダ・欠測 `-`、推計は縦持ち＋和暦列。**局ごとに様式が違い毎年変わります。**
  **LLMは値に触らずプランだけ作る**ので、ハルシネーションが数値に混入しません。
  そして `docs/13-requirements.md` §1-2 検証4 で「**そのままでは読めない**」と主張している
  当の問題を、AIで解いていることになります
- **②**：**数値は都の公式係数が出します**（§4-5）。LLMは写像だけ。
  **§0-2 のとおりトレンドがモデルを支配するので、それを自然文で動かせることが中核機能です**
- **③**：数値ルールでは全部「異常値」としか言えません。
  **江戸川区と中央区の違いは制度を読まないと分かりません**（§4-4）

## 10. 異常時の振る舞い

| 事象 | 振る舞い |
|---|---|
| `/api/scenario` が落ちる・クレジット切れ | **「解釈できませんでした」を表示。スコアとヒートマップは表示され続ける。** スライダーは動く |
| LLMが不正なJSONを返す | スキーマ検証で弾く。同上 |
| 自治体のデータが欠測 | セルをグレーで表示し「データなし」。**0点として扱わない** |
| `excluded: true` の自治体 | 色計算から除外し、表の下に別枠＋注記 |
| 射程外の年度（令和21年度以降） | **セルを描かない。**「推計の範囲外」と表示 |
| 学校データが3年分揃わない | 自治体平均の進級率で補完（§5-1） |

## 11. 技術選定

| 項目 | 選択 | 理由（提出項目③にそのまま転記できます） |
|---|---|---|
| 前処理 | **Python 3.11・標準ライブラリのみ** | 環境に導入済み。**pandas を入れない**＝3人の環境差でパイプラインが壊れない |
| フロント | **素の TypeScript ＋ Vite** | 3人全員が触れる。新規学習の余裕なし。型が契約に効く |
| スタイル | **素のCSS（カスタムプロパティ）** | Tailwindの設定に時間を使わない |
| チャート | **自前インラインSVG** | ヒートマップ＋折れ線＋予測区間の帯だけ。**書く前に `dataviz` スキルを読む** |
| 地図 | **使わない** | ジオコーディングAPIが CONNECT 403。自治体単位MVPに不要 |
| データ配信 | **静的JSON** | **実測 278KB / バンドル 501KB・gzip 159KB**。APIもDBも不要と**測定で言える**。⚠️ うち `schools` が 226KB（81%）で、これは計算に使っていない（`Muni.childrenSeries` に置き換えれば約52KBまで落ちる。docs/19 依頼2） |
| 予測計算 | **ブラウザ内（`src/core/`）** | サーバー往復が無駄。⚠️ **「都の推計モデルを再実行」ではありません**（§5-1）。実物は「都の公式推計を読む＋全都の伸び率で接続する掛け算＋自治体別の登録率トレンドの最小二乗＋バックテスト由来の予測区間」。**測っていないことを測ったように書かないため、この行を実態に合わせています** |
| バックエンド | **Pages Functions 1本**（`/api/scenario`） | 生成AI②のためだけ。APIキーをブラウザに出さない最小構成 |
| 生成AI | **Workers AI / Qwen3 30B FP8** | 事務局提供・推奨既定。**$100制約**のため実行時呼び出しは1か所 |
| DB / KV / R2 | **使わない** | 状態を持たない。**特典が間に合わなくても無料プランで動く** |
| デプロイ | **Cloudflare Pages**（ローカルから `wrangler`） | `wrangler login` はブラウザOAuthでクラウドセッションでは完結しない |

```jsonc
// package.json（②がオーナー）
"scripts": {
  "dev":    "vite",
  "build":  "vite build",                 // ⚠️ ネットに行かない。data/ を読むだけ
  "deploy": "wrangler pages deploy dist"  // ローカルマシンから実行
}
```

## 12. リスクと退避策

| リスク | 退避 |
|---|---|
| **Cloudflare特典が間に合わない**（発行1週間の可能性） | **無料プランで Pages は使える。** R2・D1 不使用なので**影響ゼロ** |
| **Workers AI が使えない／$100 を使い切る** | **シナリオをプリセット3つに退避**（マンション600戸／登録率+1pt・+2pt／供給拡大）。**完全静的で成立。** そのため `src/core` のシナリオ適用関数は**LLMと切り離したインターフェース**で切ること |
| **LLMが変なJSONを返す** | スキーマ検証＋クランプ（§7）。**スコアとヒートマップは生き続ける** |
| **①のデータが遅れる** | **`data/sample.json` を先に置く**（`docs/15-interfaces.md`） |
| **登録率トレンドが自治体で大きくばらつく**（実測 p10 +0.28pt 〜 p90 +1.87pt・豊島区は -1.82pt） | 都平均の1点を全自治体に当てていることを**注記し、スライダーで動かせるようにする**。§0-2 のとおり**感度分析ツールとして見せるのが誠実な形** |
| **軸2・3を足す時間が無い** | **v1は軸1のみで完結する設計**（§3）。プラグイン構造は「拡張性の説明」として提出文に書ける |
