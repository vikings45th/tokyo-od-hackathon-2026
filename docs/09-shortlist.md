## 候補1：使える支援制度を、世帯の状況から出す

> **「あなたの世帯が使える制度は、この12件です」**

63自治体・7,812制度を横断して、世帯の状況（子の年齢・住んでいる区市町村・
所得区分・障害の有無など）から該当しそうな制度を出す。

| | |
|---|---|
| **元テーマ** | 生活1 ＋ **デジタル1**（⭐都が唯一「自動的に届く仕組み」と明示要求）＋ 子ども・若者1 |
| **狙う賞** | **データ活用賞** / ソーシャルインパクト賞 |
| **主データ** | 子育て支援制度レジストリ（**7,812制度 / 63自治体 / 34項目 / JSON 92MB**） |
| **補助データ** | 学童クラブ事業の区市町村別実施状況（CSV）、教育人口等推計（CSV:9） |

### なぜ他チームと被らないか

57テーマの多くは「案内」型で、**検索UIを作ると埋もれます**（`docs/08-themes.md`）。
この案の中身は検索ではなく**判定**です。

対象条件（`target.targetPersons`）が**構造化されていない自然文で、平均155文字**
だからです。実物を見てください。

```
・千代田区に住民登録がある
・平成9年（1997年）4月2日～平成20年（2008年）4月1日生まれの女性
・HPVワクチンの接種を完了していない
```

```
千代田区に住み、小・中学校に在籍する児童・生徒の保護者で下記1、2のどちらかに該当する方
1.生活保護を受けている方
2.生活保護は受けていないが、これに準ずると教育委員会が認める方（前年の世帯所得が基準未満の世帯）
```

**ルールベースでは判定できません。LLMを使う理由が説明不要になります。**
「AIを使いました」ではなく「AIでないと読めないデータだった」と言える構造です。

さらに `electronicSubmission`（真偽値）が入っていて、**7,812件のうち1,179件（15%）
だけがオンライン申請可**だと分かります。「使える制度」と同時に「オンラインで
終わるか、窓口に行く必要があるか」まで出せます。行政審査員3人に効く切り口です。

### 2日で作れる根拠（実測済み）

92MBは重いので自治体別に分割します。**実際に分割を試しました。**

| | 実測値 |
|---|---|
| 世田谷区を抽出 | **163制度 / 2.4MB**（うち電子申請可50件） |
| 1自治体あたり平均 | **約1.2MB** |
| 最大の自治体 | 文京区 198制度 |

→ **1自治体1ファイルにすればブラウザで直接読める大きさです。**
前処理は「JSONを `area.areaCode` で分割して不要項目を落とす」だけ。1時間かかりません。

### ⚠️ 弱点（隠さずに書く）

- **このレジストリは2025-08-20時点で更新終了しています。**
  国（デジタル庁）の子育て支援制度レジストリへ移管済みで、
  最新データは電子申請等APIで提供されるとされています。
  → **審査基準「サービスデザイン（持続的に提供できるか）」で必ず突かれます。**
  GovTech東京CTO・デジタルサービス局長がいる審査委員構成なので、知らないふりは通りません。
  **「国のレジストリAPIに繋げば継続できる」を設計として答えられるかが勝負です。**
  逆に、そこまで言えれば加点になり得ます
- 0-6歳は JSON があるが、**7-18歳は XLSX のみ**（1.5MB）。対象年齢を広げると前処理が増える
- 一部のテキストに改行が `¥n` という文字列のまま入っている（要クリーニング）

## 候補2：世帯構成に応じた、備えと避難行動

> **「この世帯構成・この町丁目なら、備えるべきはこれ」**

町丁目単位の災害リスクと、最寄りの避難所・給水拠点を突き合わせて、
「何を備え、どこへ行くか」を世帯構成別に出す。

| | |
|---|---|
| **元テーマ** | **防災5**「世帯構成などに応じて、日常の備えと災害時の行動を提案」 |
| **狙う賞** | **ソーシャルインパクト賞** / データ活用賞 |

### 使うデータ（すべて実測済み・CC BY）

| データ | 実測した中身 |
|---|---|
| 地震に関する地域危険度測定調査 地域危険度一覧 | **5,192町丁目** × 建物倒壊/火災/災害時活動困難度のランク（CSV 356KB） |
| 東京都防災マップ 避難所・避難場所一覧 | **2,560件 / 62市区町村・全件に緯度経度**（CSV 13.8MB） |
| 給水拠点一覧データ（水道局） | **213拠点**・緯度経度・確保水量つき（CSV 44KB） |
| 浸水予想区域図（建設局／下水道局） | CSV:17 / CSV:18（神田川流域だけで40MB） |

### なぜ他チームと被らないか

**防災カテゴリ7件のうち、防災4だけが 🔥 経路案内型で、防災5は違います。**
経路案内は57件中9件で最激戦区、しかも2025年度の都知事杯受賞作と同型です
（`docs/08-themes.md`）。**そこを避けつつ、防災の切実さは使えます。**

そして地域危険度が**町丁目単位で5,192件**あるのが効きます。「東京都は危険です」
ではなく「あなたの町丁目は建物倒壊危険度ランク4です」と言えます。粒度が価値です。

### 2日で作れる根拠

**主要データが全部CSVで、合計400KB程度**（浸水予想図を除く）。
避難所13.8MBも実データは2,560行だけです（下の落とし穴を参照）。
地理計算は「最寄りN件」を出すだけで、経路探索は不要です。

### ⚠️ 弱点

- **避難所CSVは実データ2,560行に対し、総行数が1,046,315行**あります。
  Excel書き出しの空行が約104万行付いています。素直に読み込むと固まります。
  ヘッダも1行目ではなく**2行目**です
- 浸水予想区域図は流域別に分かれていて、**神田川流域だけで40MB**。全流域は重い。
  対象エリアを絞る判断が必要
- 「世帯構成に応じて」の部分に**世帯構成のデータは無い**ので、ここはユーザー入力です。
  データ活用の主役は危険度・避難所側だと割り切ること

## 候補3：698万行から出す「運動していい時間帯」

> **「この公園でウォーキングするなら、この時間帯」**

PM2.5の1分値の履歴から、測定局ごと・時間帯ごとの傾向を出し、
近くの公園やウォーキングコースと重ねる。

| | |
|---|---|
| **元テーマ** | 環境4（大気の可視化）× 健康・スポーツ2（無理のない健康づくり） |
| **狙う賞** | **技術賞** / データ活用賞 |

### 使うデータ（実測済み）

| データ | 実測した中身 |
|---|---|
| PM2.5モニタリングデータ（1分値・過去50日分） | **ZIP 17.8MB → 展開165MB / 8ファイル / 698万行 / 82局**、2026-07-01〜**08-19** |
| 測定局所在地データ | **81局**・緯度経度つき（CSV 8.5KB） |
| 都立公園・庭園一覧 | CSV |
| TOKYO WALKING MAP | **KML 264本**（コース単位。都が3カテゴリで推しているデータ） |

### ⚠️ この案は docs/04-ideas.md の「方向1」から前提を変えています

`docs/04-ideas.md` は「PM2.5 1分値は唯一の準リアルタイムデータ。閾値超過で
**通知**できる」としていましたが、**実測の結果それは成立しません。**

| 項目 | 実測値 |
|---|---|
| 更新頻度 | `last-modified` 2026-08-19 16:19 GMT（= 8/20 01:19 JST）→ **日次** |
| データ最終時刻 | **2026-08-19 24:00**（＝前日分まで） |

**リアルタイムではなく「1分粒度の履歴が日次で追加される」データです。**
「今この瞬間、外に出ていいか」は作れません。**「いつ出るのがいいか」に振れば成立します。**

### 2日で作れる根拠

698万行の集計はローカルなら数分です。**前処理して「局×時刻×統計値」に
畳めば数十KB**になり、ブラウザで軽く動きます。技術的な見せ場はここです。

### ⚠️ 弱点

- **CP932・ヘッダ行なし・ZIP配布・165MB。** `CLAUDE.md` が推す「ブラウザ実行時に
  クライアント側から取得」は**不可能**です。前処理してコミットする以外にありません
- 列は `局コード,項目コード,年,月,日,時,分,値` の8列で、**列名がどこにも書かれていない**。
  別途「測定項目リスト」CSVと突き合わせる必要があります
- 時刻が `24:00` 表記で出てきます（`00:00` ではない）。素直にパースすると落ちます
- **「涼しい時間」ではなく「空気がきれいな時間」です。** 8月開催で暑さの話をしたく
  なりますが、このデータは気温を持っていません。混ぜると論点がぼやけます

## 候補4：数年後に学童が足りなくなる地域を予測する

> **「あなたの区は3年後、学童が何人分足りない」**

都の公式推計（区市町村別・5年後まで）と、現在の学童クラブの待機児童数を
突き合わせて、不足が起きる地域と時期を出す。

| | |
|---|---|
| **元テーマ** | 子ども・若者1 ＋ 生活1（＋ デジタル3 の可視化） |
| **狙う賞** | **アイデア賞** |

### 使うデータ（実測済み）

| データ | 実測した中身 |
|---|---|
| 教育人口等推計（教育庁） | `25es_result02` に**地区名（区市町村）× 令和7年度〜5年後の公立小学校児童数推計**（69行・7KB）。ほか CSV 9本 |
| 学童クラブ事業の区市町村別実施状況（福祉局） | **区名・市町村名 × クラブ数・登録児童数・待機児童数**（71行・2.4KB） |

### なぜ他チームと被らないか

**57テーマを型で分けると「シミュレーション・予測」型は3件しかありません**
（`docs/08-themes.md`）。残りは案内・マッチング約30件、可視化約10件です。
**「現状を可視化しました」の海の中で、未来を出す案はほぼ来ません。**

しかも `docs/04-ideas.md` が掛け合わせの推奨例として自ら挙げている組み合わせです
（「学童クラブ実施状況 × 教育人口推計 → 数年後に不足する地域の予測」）。

そして**予測の根拠が都自身の公式推計**なので、「その数字は本当か」に耐えます。
行政審査員3人がいる構成では、これは強い性質です。

### 2日で作れる根拠

**データが合計10KB未満です。** 5案の中で最軽量。前処理はほぼ不要で、
残り時間を全部「見せ方」に使えます。

### ⚠️ 弱点

- **学童クラブのデータが令和5年5月1日現在**で、2年古い。推計は令和7年度起点なので、
  基準年がずれます。ここを正直に扱わないと数字の信頼を失います
- ヘッダが**5行目**で、区部と市町村部が**横に並んだ2ブロック構成**の
  Excel由来レイアウト。素直に読めません
- **データが軽い＝「データ活用」で点を取りにくい。** 使うデータが2件だと
  「オープンデータが本質的に効いているか」で伸びません。狙うならアイデア賞一本です

## 候補5：車椅子・ベビーカーの視点で施設情報を突き合わせる

> **「その避難所、車椅子で入れますか」**

バリアフリー情報を持つ複数のデータを突き合わせ、「誰にとって使えるか」で
施設を絞り込めるようにする。

| | |
|---|---|
| **元テーマ** | 交通3（**車椅子やベビーカーなど、状況に応じた案内**）＋ 防災1 |
| **狙う賞** | **サービスデザイン賞** |

### 使うデータ（実測済み）

| データ | 実測した中身 |
|---|---|
| 東京都防災マップ 避難所一覧 | 2,560件中、**エレベーター/スロープ/点字ブロック/車椅子使用者対応トイレ**の4項目つき。車椅子トイレ記載は**651件** |
| だれでも東京（宿泊施設） | **273施設**・緯度経度・バリアフリー項目（CSV 267KB） |
| 公共施設一覧（デジタルサービス局） | CSV 129KB |

### なぜ他チームと被らないか

交通3は 🔥 経路案内型（9件・最激戦区）ですが、**「誰のための経路か」が
テーマ文に最初から書いてある唯一の項目**です。差別化の軸がデータ側にあります。

そして**「2,560ある避難所のうち、車椅子対応トイレがあると書かれているのは651件だけ」
という事実自体がメッセージになります。** 可視化がそのまま主張になる構造です。

### 2日で作れる根拠

CSV3本、合計400KB程度。地図に置いて絞り込むだけで成立します。

### ⚠️ 弱点

- **経路案内型に踏み込むと最激戦区**です。経路を作らず「絞り込みと可視化」に
  留める判断が要ります
- だれでも東京は**空列が非常に多い**（宿泊施設273件に対し列が数十あり大半が空）。
  「情報が無い」のか「対応していない」のかが区別できません。ここを誤ると
  当事者にとって有害な情報になります。**扱いに最も注意が必要な案です**
- サービスデザイン賞はデザインリソースが要ります（`docs/04-ideas.md`）。
  3人にデザインできる人がいないなら不利です

## ⛔ 足切り済み（実測で落ちた案）

**ここを再度議論するのは時間の無駄です。** 落ちた理由は実測です。

### 3Dマップによる日影ルート（docs/04-ideas.md 方向2）

`都市の３Dデジタルマップデータ` の53リソースは**実ファイルではなく、
G空間情報センター（PLATEAU）の区市町村別データセットページへのリンク**でした。
形式は cityGML。

そして **`www.geospatial.jp` / `plateau.geospatial.jp` はこの環境から遮断**
されています（CONNECT 403）。**データ取得の入口すら通っていません。**

審査委員に Eukarya（Re:Earth）の田村氏がいるので惜しい案ですが、2日では無理です。

### 都営バス・地下鉄の GTFS-RT を使う案

`東京都交通局 都営バス・都営地下鉄オープンデータ`（CC BY・17リソース）には
**GTFS-RT（バスロケーション情報）**・列車ロケーション情報・運行情報 JSON があります。
**PM2.5より本物のリアルタイムです。** それでも落とします。

- 説明文に「**公共交通オープンデータセンターにユーザー登録することでご利用いただけます**」
  → 登録とAPIキーが必要。**承認待ちが8/23に直撃する**
- **`ckan.odpt.org` / `api.odpt.org` もこの環境から遮断**（CONNECT 403）。
  許可リストへの追加も別途必要

→ 外部の承認と環境設定の2つに依存します。残り2日では賭けになります。
**8/23を過ぎたら何もできません**（`CLAUDE.md`）。

### 都税収入の可視化（生活6「税の使い道の見える化」）

**当初これを候補に入れる予定でしたが、実測で落ちました。**

- `都税収入見える化ダッシュボード　データ一覧` の **41リソース全部が HTTP 404**。
  主税局の「お探しのページは見つかりません」ページが返ります（HEADでもGETでも同じ）
- そもそも**都の歳出・予算データがほぼ存在しません**（財務局はPDFのみ）。
  テーマ名は「**使い道**」なのに、収入側のデータしか無い

審査委員に Zaim 創業者の閑歳氏がいるので魅力的な方向ですが、**データが無いので
成立しません。** カタログに登録されていても実ファイルが生きているとは限らない、
という教訓として残します。

### 防犯3「夜間の安全な移動経路の案内」

**2025年度都知事杯受賞作そのものです**（`docs/04-ideas.md`）。
去年と直接比較されます。「去年より何が良いか」を2日で示せるなら別ですが、

## 採点表（各自コピーして埋める）

`docs/04-ideas.md` の評価マトリクスをそのまま使います。**各5点満点・合計25点。**

| 審査基準 | 採点の観点 |
|---|---|
| データ活用 | そのオープンデータが無いと成立しないか。何件・どう組み合わせるか |
| アイデア力 | 既存サービス・他チームの発想とどう違うか。サービスとして成立しているか |
