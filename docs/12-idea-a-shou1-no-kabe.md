## 1. ターゲットと、解決する課題

### 想定ユーザー（主）

**これから東京で家を買う・借りる、0〜5歳の子がいる共働き世帯。**

- 保育園には入れた（あるいは入る目処が立った）
- いま住まいを探している、または住宅ローンを検討している
- 東京都は転入超過が続いており、**この層は毎年新しく発生し続ける**

### 想定ユーザー（副）

**すでに小学校入学が数年先に迫っている保護者**（引っ越さないが、民間学童の
予算取りや働き方の判断を前倒ししたい層）。同じ画面で足りる。

### ペイン

> **「保育園には入れた。でも小1で詰んだ。」**

学童に入れないと、放課後に子どもの居場所が無くなる。結果として親（多くは母親）が
**時短・退職に追い込まれる**——これが「小1の壁」。
審査基準の「**手取り時間の増加等、都民のQOL向上**」に真正面から当たる。

**そしてこの痛みは、住まいを決めた後では手遅れ。** 住宅ローンを組んだ人は動けない。

### いま、この人たちはどうしているか

| 情報源 | 出てくるもの |
|---|---|
| 不動産サイト | 学区名と、学校までの距離 |
| 区のサイト・PDF | **今年の**待機児童数 |
| SNS・口コミ | 個人の体験談 |
| 区役所に電話 | **今年の**空き状況 |

**すべて「現在」の情報。** 誰も未来を出していない。

### なぜ予測でないと解けないのか

**意思決定する時点と、痛みが出る時点が最大6年ずれる。**

```
2026年  0歳の子がいる。家を買う ← 意思決定はここ
                ↓ 6年
2032年  子が小1になる。学童に入れない ← 痛みはここ
```

**今年の待機児童数は、6年後の判断材料にならない。**
この6年のズレこそが、このサービスの存在理由。

### 予測を見た人が打てる手

これが無いと、ただ不安を煽るだけになる。**画面に必ず出す。**

- 検討している街を選び直す（近隣の学区と比較する）
- 住み替えの時期を、入学年度に合わせてずらす
- 民間学童の費用を、最初から資金計画に織り込む
- 保育園を選ぶ段階で、学童併設・学校併設を条件に入れる

### 効果の見込み（提出フォームに書く文）

- **調べる時間**：区役所への問い合わせ・PDF探し・SNSでの噂集めが、1画面に置き換わる
- **失う時間**：小1の壁による離職・時短は**年単位の就労時間**を失わせる。
  そこに先回りできること自体が効果

> ⚠️ **「◯時間削減」を根拠なく書かないこと。** このサービスの価値は
> 「調べる時間の短縮」ではなく「**取り返しのつかない意思決定を間違えないこと**」。
> そう書いた方が強く、かつ正直。

## 2. 何を作るか（2分動画で映る1画面・1シナリオ）

```
[入力]  子どもの生まれ年       → 小1になる年度が決まる
        検討している区市町村   → 学校を選ぶ

[出力]  ① その学校の児童数の推移（実績3年 ＋ 予測5年・学年別）
        ② 子が小1になる年の学童の需給ギャップ（人）＋ 予測区間
        ③ 今この区で起きていること（待機児童数・クラブ数・制度の注記）
        ④ 打てる手（近隣学区との比較）
        ⑤ シナリオ入力（自然文）→ 再計算
```

**「あなたの子が小1になる2032年、この学校の学区では学童が◯人分足りません」**
——これが2分動画のクライマックス。

**⛔ これ以外は作らない**（`docs/10-roles-schedule.md` §6）。地図・ログイン・
複数条件検索・エクスポートは最初から捨てる。

### すでに走らせた検証

**バックテスト**（令和5年度版の推計が出した令和7年度値 vs 令和7年度実数・57地区）：

```
平均誤差 +0.26% / 中央値 +0.50% / 絶対誤差平均 1.51%
最大の外し：島部 -6.02% / 国立市 -5.57% / 江東区 +4.13% / 日の出町 +5.18%
```

**学童の需要率**（令和5）：

```
都計：登録132,648 / 全学年594,121 = 0.223  （低学年299,522 基準なら 0.443）
上位：渋谷区0.447 千代田区0.382 板橋区0.336 港区0.313 豊島区0.305
下位：足立区0.172 大田区0.177 稲城市0.178 府中市0.189 中野区0.190
```

**外れ値が2種類ある。区別しないと人に害が出る。**

| | 実測 | 正体 |
|---|---|---|
| ⛔ **江戸川区 0.009** | 登録141人・クラブ4か所 | **制度が別枠**（全児童対象の「すくすくスクール」）。データは壊れていない |
| ⚠️ **中央区 0.088** | 登録774人・15クラブ・**待機257人** | **本物の供給不足**。率が低いのは需要が無いからではなく受け皿が無いから |
| ⛔ 利島村1.455 / 三宅村1.431 | 母数11人・51人 | 島嶼部は比率が壊れる |

**3つを同じ「異常値」として潰すと、中央区の実害が消える。**
引っ越し判断に使うサービスでそれをやってはいけない。**外れ値処理は機能の中核。**

## 4. 予測アルゴリズムと、生成AIの3か所

### 数値は全て決定論的に計算する。LLMに数字を作らせない。

1. **学校別コーホート進級率**：`r(school,g) = 児童数(R7,g+1) / 児童数(R6,g)`、R6/R5でも同様
   → **2年分の平均**。`[0.7, 1.3]` でクリップ。欠測校（統廃合・新設）は区市町村平均で埋める
2. **新1年生**：区市町村の `就学予定者` 推計を、**その学校の過去3年の1年生シェア**で按分
3. **前進**：t+1年の各学年 = t年の1つ下の学年 × 進級率。1年生は 2. から
4. **raking（整合）**：学校合計が**都の公式推計（区市町村×学年）に一致するようスケーリング**。
   **都の推計を否定せず、細分化するだけ**という立て付け。行政審査員3人に効く
5. **需要**：`将来児童数 × 学童登録率（区市町村別・全学年基準）× シナリオ倍率`。
   低学年（1〜3年）の推移も**別指標として併記**
6. **供給**：現在の登録児童数を据え置き。待機児童数で現在の逼迫を較正
7. **ギャップ** = 需要 − 供給。**予測区間はバックテストの実測誤差分布から**

> ⚠️ **3年以上先の誤差は測れない。** 推計ヴィンテージが3世代しか無いので、
> 実測できるのは**1年先と2年先だけ**。それ以降は外挿だと明記する。
> **測っていないことを測ったように書かない**のが、この案の生命線。

### 生成AIの3か所

| # | 役割 | いつ動くか | なぜAIでないと駄目か | 担当 |
|---|---|---|---|---|
| **①** | **様式不定CSVの読解ETL**。先頭30行をLLMに渡し「ヘッダ行番号・列対応・ブロック分割・数値クリーニング規則」の**JSONプラン**を生成させ、決定論的パーサがそれを実行 | 前処理で1回。プランを `scripts/plans/*.json` に**コミットして固定** | 学童CSVはヘッダが5行目・区部と市町村部が横並び2ブロック・`"1,261 "` 形式、学校一覧はCP932・多重ヘッダ・欠測 `-`、推計は縦持ち＋和暦列。**局ごとに違い毎年変わる。LLMは値に触らずプランだけ作る**のでハルシネーションが混入しない | ① |
| **②** | **自然文シナリオ → 公式係数へのパラメータ変換**。「駅前に600戸のマンションが2028年完成」「学童を6年生まで拡大」「登録率が5年で10ポイント上昇」を、`25es_survey`・`25es_iadtable` の**どの係数をどこに幾つ適用するか**に翻訳 | **実行時**（Workers AI） | **数値はLLMではなく都の公式係数が出す。** LLMは「言葉→係数の選択と適用先」の写像だけ。**これが「予測に生成AIを使う」の核** | ② |
| **③** | **制度差・外れ値の判定と注記生成**。江戸川区（制度が別枠）／中央区（本物の不足）／島嶼部（母数不足）を**区別**して注記を書く | 前処理で1回。`data/app/notes.json` にコミット | 数値ルールでは全部「異常値」としか言えない。**なぜ違うのかは制度を読まないと分からない** | ① |

> ⚠️ **Workers AI のクレジットはチーム$100・追加は承認制**（`docs/05-tech.md`）。
> ①③を前処理に寄せ、実行時に呼ぶのは②だけ。
> **この設計理由がそのまま提出項目③「生成AI等の活用方法」「技術選定の理由」になる。**

## 5. 3人の分担

`docs/10-roles-schedule.md` の縦割り（ディレクトリ境界＋出荷オーナー）をそのまま使う。

| | 開発担当（自分のディレクトリ） | このプロダクトでの中身 | 出荷オーナー |
|---|---|---|---|
| **①データ** | `scripts/` `data/` | 8データセットの取得・**LLM①のETL**・正規化・**LLM③の注記**・`SOURCES.md` | **提出フォーム**（①〜⑥・約1,800字） |
| **②ロジック/AI** | `src/core/` `src/api/` | **予測エンジン**（コーホート・raking・バックテスト）・**LLM②のシナリオAPI** | **デプロイと公開URL** |
| **③UI** | `src/ui/` | 入力・結果表示・チャート・注記・**出典表記** | **スライド・キャプチャ・動画台本** |

### なぜこの割り方か

- **予測エンジンを `scripts/`（Python）ではなく `src/core/`（TypeScript）に置く。**
  ①が正規化まで、②が予測計算、と切ると**ディレクトリが衝突しない**。
  データ量は1,255校×6学年×3年 ≈ 22k数値で、ブラウザで回して一瞬。
  副次的に「**ブラウザ上で都の推計モデルを再実行している**」という技術的見せ場になる
- ①はデータ整形が Day1 で終わるので、Day2 に提出フォーム（2時間）を持てる
- ②はビルドと Workers を触るので、デプロイで壊れたとき直せるのが本人
- ③は画面を一番分かっているので、キャプチャと動画台本を持つべき

### 契約（11:15–12:00・全員）— **ここが最重要**

待ちが出た時点で負ける。**実装前に型とダミーを置く**（`docs/10-roles-schedule.md` §2）。

`src/types.ts`（**②が起票・3人で合意・以降は極力動かさない**）の骨子：

```ts
export type School   = { id: string; muni: string; name: string; address: string };
export type Actual   = { id: string; years: number[]; grades: number[][] };  // 年度 × 1〜6年生
export type Muni     = {
  name: string;
  official:  { year: number; grades: number[] }[];   // 都の公式推計 令和7〜12
  entrants:  { year: number; count: number }[];      // 就学予定者
  gakudo:    { clubs: number; registered: number; waiting: number; asOf: string };
  rate:      number;                                  // 登録率（全学年基準）
  note?:     { kind: 'system-difference' | 'real-shortage' | 'small-sample'; text: string };
};
export type Backtest = { horizon: 1 | 2; mae: number; p10: number; p90: number };
export type Scenario = {
  housing?:  { schoolId: string; year: number; units: number; type: HousingType }[];
  rateDelta?: number;        // 登録率の年あたり変化
  targetGrades?: number[];   // 既定 [1,2,3]
};
export type Projection = {
  schoolId: string; years: number[];
  grades: number[][]; lowerGrades: number[];
  demand: number[]; supply: number; gap: number[];
  band: { lo: number[]; hi: number[] };
};
```

`data/sample.json`（**①が作る・実データ不要**）：この型に沿ったダミー10校。
**これがあれば②③は実データを待たずに書き始められる。**
