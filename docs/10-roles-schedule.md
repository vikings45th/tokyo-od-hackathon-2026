# 役割分担とタスクスケジュール（3人・全員オンライン）

**前提**：3人とも開発したい／全員オンライン参加／会場時間は 10:00–20:00 だが、
人によってはそれ以降も作業できる／AIは積極的に使う。

> ⏰ **いまは 8/22（土）朝。提出締切は 8/23（日）17:00 = 残り1.5日です。**
> **テーマと狙う賞は今日の午前中に決めます。** `src/` はまだ空です。
> このスケジュールは**今朝から始まります**。

---

## 1. 役割の考え方

### 「開発担当」と「出荷オーナー」を分ける

3人とも開発したい。一方で提出物はプロトタイプだけではありません
（スライド・約1,800字のエントリー項目・出典リスト・公開URL）。
これを1人に寄せるとその人は開発できず、全員で持つと誰も責任を持ちません。

そこで**2階建て**にします。

- **開発担当**：ディレクトリ境界で縦割り。**3人ともコードを書く**
- **出荷オーナー**：提出物ごとに1人。**作業は全員でやる／責任だけ1人が持つ**

> オーナーは「その提出物を1人で作る人」ではありません。
> **「8/23 17:00 にそれが出ていることを保証する人」**です。
> 下書きはAIに書かせ、全員でレビューします（§5）。

### 割り当て

| | 開発担当（自分のディレクトリ） | 出荷オーナー |
|---|---|---|
| **① データ** | `scripts/` `data/` — 取得・整形・アプリが読むJSONを吐く | **提出フォーム**（エントリー項目①〜⑥の記入と送信） |
| **② ロジック/AI** | `src/core/` `src/api/` — 判定・集計・Workers・LLM呼び出し | **デプロイと公開URL**（`package-lock.json` のオーナー兼任） |
| **③ UI** | `src/ui/` — 画面・入力・結果表示・出典表記 | **スライド・画面キャプチャ・動画台本** |

**①②③を実名に置き換えてください。決めたらこの表を書き換えてコミット。**

#### なぜこの組み合わせか

- **①データ ＋ 提出フォーム**：データ整形は Day1 でほぼ終わるので、Day2 に手が空くのが①です。
  提出作業（2時間見る）を持てるのはここ。加えてエントリー項目⑤
  「オープンデータの利用状況（最大10件）」は `data/SOURCES.md` の転記なので、**同じ人が持つのが最速**
- **②ロジック ＋ デプロイ**：ビルド設定と Workers を触るのが②。デプロイで壊れる原因の大半はここなので、
  **触っている本人が直すのが最短**。生成物（lockfile）のオーナーを1人に固定するルール
  （`docs/07-team-workflow.md`）もここに寄せます
- **③UI ＋ スライド**：画面キャプチャを撮るのも、2分動画で何を映すか決めるのも、
  **画面を一番わかっている人**がやるべきです

### 全員が守ること

- **自分のディレクトリの外を大きく書き換えない。** 3人がAIを回すと一瞬で衝突します
- ブランチは `feat/<名前>/<機能>` の短命ブランチ。push 前に必ず `git pull --rebase`
- **30分動かなかったら必ず声を上げる。** 抱え込むと縦割りが単一障害点になります

## 2. 待ち時間をゼロにする「契約先行」【最重要】

縦割りの最大リスクは **「①のデータが出来るまで②③が待つ」** です。
1.5日しかないので、待ちが出た時点で負けます。

**実装を始める前に、契約を先に決めてダミーデータを置いてください。**

```
src/types.ts        … アプリが扱うデータの型（②が起票、3人で合意）
data/sample.json    … その型に沿ったダミー10件（①が作る・実データ不要）
```

これがあれば：

- **②③は実データを待たずに書き始められる**
- ①は「`sample.json` と同じ形の本物を作る」だけになり、迷いが消える
- 実データ差し替えは Day1 午後の1回で済む

> ⚠️ **型を変えたくなったら、勝手に変えずに必ず3人に言ってください。**
> 型の変更は3人全員の手を止めます。今日の昼までに決めて、以降は極力動かさない。

## 4. オンライン運用のルール

全員オンラインなので、**会場の 10:00–20:00 は「3人が確実に揃っている時間」という意味**
以上でも以下でもありません。会議を増やすと溶けます。

- **常時つなぎっぱなしの音声チャンネルを1つ用意する**（Discord / Zoom どちらでも）。
  無言でよい。詰まったら喋る、が一番速い
- **同期は1日3回・各15分だけ**（朝会 / 中間 / 締め）。それ以外は非同期
- 進捗は口頭ではなく **`docs/02-todo.md` のチェックボックス＋push** で共有する
- Zoomのブレイクアウトルームが要るなら当日 `#03_事務局への質問` で依頼できます

### 会場時間外（20:00以降）のルール

作業できる人が続けるのは歓迎ですが、**翌朝に他の2人を止めないこと**が条件です。

| 夜にやってよい | 夜にやってはいけない |
|---|---|
| 自分のディレクトリ内のバグ取り・磨き込み | **型定義やディレクトリ構成の変更** |
| 文章（エントリー項目・スライド・台本） | **他人のディレクトリのリファクタ** |
| データの追加整形、テスト追加 | **依存パッケージの追加・lockfile の更新** |

**夜の作業も必ず push してから寝てください。** クラウドセッションのVMは回収されます。

## 5. AIの使い方（3人とも積極活用）

### 分担

| AIに任せる | 人間が必ず確認する |
|---|---|
| 実装・テスト・CSVの文字コードや欠損処理 | **データの出典とライセンス表記**（間違うと大会ルール違反） |
| スライドの構成案・エントリー項目の下書き | **提出フォームに出す最終文言** |
| ダミーデータ生成、リファクタ、命名 | **デモの筋書き（2分で何を見せるか）** |
| 調査・要約 | **公開URLが本当に動くか** |

### チームとしてのルール

- **設計判断はプランモードで。** 3人が別々の前提で書き始めるのが最悪です
- **1人1セッションを基本に。** レート制限はアカウント全体で共有です。
  並列セッションを増やすほど早く枯れます
- **同じファイルを2人が同時にAIに書かせない**

### 「生成AIをどう活用したか」をログに残す

エントリー項目③に **「技術選定の理由」「生成AI等の活用方法」** の記入欄があります
（`docs/05-tech.md`）。審査基準「技術力」に直結します。

→ **[`docs/11-ai-log.md`](11-ai-log.md) に、AIに何をやらせたかを1行ずつ足してください。**
Day2 に思い出そうとしても出てきません。**その場で1行書くだけ**で、提出文がタダで手に入ります。

## 6. 崩れたときの判断基準

うまくいかないのが普通です。**迷ったらこの順で捨ててください。**

| 捨てる順 | 対象 |
|---|---|
| 1 | **見せ場以外の機能**（設定画面・複数条件・エクスポート等）。最初から作らない |
| 2 | **実データの網羅性**。1自治体分・1カテゴリ分で動けば作品として成立します |
| 3 | **UIの作り込み**。スライドと動画で伝わればよい |
| **絶対に捨てない** | **公開URLで動くこと／出典とライセンス表記／エントリー項目①〜⑥／スライド** |

**プロトタイプが100点でも、スライドと文章が無ければ審査対象になりません。**
逆に機能が1つでも、動いて・出典が明記されて・語れれば、5基準のうち複数で点が入ります。

### 誰かが落ちたら

縦割りは単一障害点になります。**毎日 20:00 の push が引き継ぎポイント**です。
残り2人でやるときは、上の「捨てる順」を1段深く適用してください。
